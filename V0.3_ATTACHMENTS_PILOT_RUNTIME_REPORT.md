## Análise do ponto de falha

A mensagem exibida é o fallback de Backend.error (Backend.kt:194, else). Esse caminho cobre exceções não mapeadas — tipicamente:

1. requestAttachmentUpload lança erro interno de servidor (interrupção na geração da URL assinada V4 via getSignedUrl) — quando o bucket remoto não está disponível/resolvido para o projeto, ou a identidade de execução não tem permissão iam.serviceAccounts.signBlob / criação de objetos no bucket, ou a Storage e a API de credenciais do service account não estão habilitadas no projeto.
2. uploadBytes falha no HTTP PUT à uploadUrl (código fora de 2xx e diferente de 412) — a exceção levantada (Exception com a mensagem "Falha no envio do arquivo (HTTP ...)") é também convertida no fallback genérico, encobrindo a causa.

Ambas as possibilidades apontam para a camada remota de Storage/assinatura compartilhada entre ocorrências e rondas; o pipeline cliente (AttachmentsUi.kt, Backend.kt, MainActivity.kt) e o código backend (backend/src/attachments.js, idêntico ao snapshot) não apresentam defeito identificado na revisão estática, e o adapter de Storage foi testado apenas com doubles locais (nunca contra o Storage remoto) — conforme V0.3_FINAL_REPORT.md, itens 4-5 da seção "DEPLOY NECESSÁRIO PARA PILOT", que registram como pendentes: bucket padrão resolvendo para cirene-9d83e.firebasestorage.app, permissões de leitura/escrita de objetos e signBlob na conta de execução das Functions, bem como habilitação da API necessária.
